# Proposed actual four-node acceptance (not executed)

This is the next-stage design, pending accepted Task10 fixes, fresh committed app/config hashes, and root approval. The outer platform proof does not prove installed product behavior. The minimal nested canary and every later installed gate retain separate evidence.

## Topology, control and disk gate

Keep the existing zero-NIC VZ outer at 2 CPUs, 3 GiB and an 8 GiB logical disk. Use four persistent private nspawn roots: green primary/secondary `.21/.22` and synthetic original primary/secondary `.31/.32`. Guest-only auxiliary namespaces host the synthetic API `.10`, TLS PostgreSQL `.11`, and NAS `.40`. One unrouted bridge, no host listeners/shares, no default routes; exact peer/API/PG/NAS firewall permits only. Metadata is node-local on `169.254.169.254`; fixed vendor DNS names resolve only inside these namespaces to the synthetic endpoint with a fixture CA trusted only in the guest. No shipping endpoint override or injected client implementation.

A guest-root controller, staged on a read-only seed, runs each real CLI through the registered machine's actual PID/mount/network/cgroup namespaces. It verifies machine name, distinct machine ID, current boot ID, namespace ownership and enrolled receipt public pin before each operation. Protected transfer uses a private local root-to-root pipe between those authenticated owned namespaces, fixed allowlisted paths, no-follow open, new atomic mode0600/root-owned destination and digest/signature verification. Private bytes never cross serial output. The product independently verifies the genuine pinned receipt signatures. This replaces SSH transport only; it does not mint a receipt or bypass any protected CLI check. Root must review this concrete transport implementation before full execution.

Reuse one immutable common native package layer plus distinct persistent overlays; keys, configuration, machine IDs, runtime directories, source state, receipts and collector backing files are always per-node. A naïve four-way copy is out of budget. Measure actual installed sizes first. Propose an offline shared package layer using the exact62 archives with package starts blocked and no app configuration/activation; normal green prepare must still verify this real installed package state and perform its genuine transaction. Root must approve this preparation strategy before use. A read-only guest bind of the frozen outer base with opaque private state directories can avoid a second full base copy, but requires an explicit exposure/immutability audit before adoption. Otherwise retain the measured copied lower root if it fits. Reserve both real512MiB collector images, PG/CA data, queue bounds and at least1GiB free; stop before crossing the disk/memory ceiling. Do not shrink the product collector or replace package files. The currently cached ARM64 shipping bundle is225MiB; final app/bundle/dev seed must remain under the runner's512MiB read-only seed limit.

## Original source and cloud seed gate

Generate only synthetic secrets inside the private guest: original EC and RSA root/intermediate/decrypter keys and certificates, valid original provisioners/templates, separate existing `stepca`/`stepca_rsa` PostgreSQL databases and owners, original server certificate/key cache, shared Class key, webhook key/certificate and stable KMS version identities. Generate the TLS PG CA and distinct runtime/native/migration roles according to the final reviewed pool/privilege contract. Record public hashes and private file continuity, never private content. Do not add accounting history to green or replace CA state during prepare.

Original source nodes need real valid native configurations/services, not the placeholder bytes from `parallel_source_linux_test.go`. Render/review the preserved legacy native templates with only fixture identities and private endpoints; inventory any additional runtime prerequisites before acquiring/installing them. Actual source RADIUS and both CAs must be running before capture and remain running while real known writer units/helpers/crons are fenced. A small synthetic writer workload at the exact legacy paths may exercise locking/fencing, but is labeled a synthetic workload, not the original vendor implementation.

Seed the actual legacy paths consumed by capture: `/etc/freeradius/3.0/radiusd.conf`, `device-policy-cache.json`, `/var/lib/cloud-8021x/certificate-state.json`, original Class/downgrade guard, valid `/etc/step-ca{,-rsa}/certs/{root_ca,intermediate_ca}.crt`, both `config/ca.json` files, the Wi-Fi ACME/SCEP templates, and `/etc/acme-authz-webhook/server.{crt,key}`. Policy fingerprints, original observation timestamps and pending-command provenance must be internally consistent and independently validated. Follow the exact known writer paths in `internal/privileged/host/writers.go`; no fabricated fence state. Preserve file bytes before/after adoption and reversal.

The existing Go cloud helper still needs stateful Secret Manager publication, Fleet pending/uncertain/terminal command lifecycle, provider pagination/failure scenarios, and actual OTLP payload decoding/receipt reconciliation. Its current metadata/Secret Manager/KMS REST+gRPC/static-route tests are primitive tests only. Before whole-flow work, prove actual shipped step-ca Google SDK TLS/ADC/GetPublicKey/AsymmetricSign interoperability and issuance against these exact synthetic identities. Record actual sign calls and verify issued chains with their preserved roots. This proves wire/SDK interoperability against a local remote mock; it does not prove GCP IAM, production KMS/HSM, actual Fleet delivery, or Datadog backend processing. Unknown methods/paths, internet and passive mutations remain denied.

## Ordered shipping workflow and acceptance gates

1. Stage fresh reviewed exact app/62 manifests, strict role YAML and `postgres-ca.pem` at `/var/cache/cloud-8021x/artifacts` on all four nodes. Validate YAML unprivileged. Run the actual staged `cloud-8021x bootstrap source-key --incoming` on each node, collect four distinct public pins through the owned controller, render/freeze the final pair and source configuration, epoch and release identity. Never copy receipt private keys between overlays.
2. On each source run `bootstrap capture --incoming`; transfer its real `parallel-radius-{primary,secondary}.json` to the corresponding green fixed artifact path. Run actual `bootstrap prepare --incoming` on each green. Audit installed binary/unit/native/CA files and real stopped services. Attempt prohibited passive starts, reboot both nodes, require changed boot IDs and persistent barriers. Hash journal segments to prove no passive KMS sign, secret publication, Fleet submission or business export. Verify real empty green accounting epoch and preserved original certificate guards/timestamps.
3. Refresh both captures immediately before cutover (source proofs expire after ten minutes), transfer and re-run prepare on each completed green. Run installed `/usr/local/bin/cloud-8021x bootstrap activate` on primary, secondary, primary. Observe real waiting-for-peer then enabled shared epoch, actual native/CA/worker/collector PID1 units/cgroups, root activation authority and the product's512MiB loop mount. No hand-written marker or success receipt.
4. Use the independent NAS helper against the installed RADIUS listeners: real EAP success/rejection and exact numeric VLAN13/6/Class, signed accounting Start/Interim/Stop and independent SQL rows/deltas. First ongoing Interim/Stop credits zero; subsequent exact deltas, duplicates and restart recovery retain correct epoch semantics. Exercise stale inventory/downgrade rejection. Stop one green's real services/node and prove peer authority and continued packet behavior; restore/reboot and audit continuity.
5. Interrupt only the owned PG service/network and synthetic intake. Generate bounded real traffic, verify outage behavior, durable spool/ledger retention, later replay without duplicate credit and collector queue/reboot recovery. Verify actual DDOT requests and decoded event identities against the exact SQL/outbox receipt state; HTTP200 alone is insufficient. Keep CA and app data in distinct supported schemas/databases. Do not claim mock intake equals real Datadog delivery.
6. Run installed `bootstrap deactivate` on both greens, reboot and verify persistent real worker/native fences and revoked epoch. Demonstrate `bootstrap rollback-proof` refusal before the second physical fence and again while an actual pending/uncertain certificate command remains unresolved. A missing/404 command response stays unresolved. Reconcile only retained exact work with `state recover-collection --guard … [--execution-id …]` or `state recover-work --kind fleet-terminal --work … --generation … --payload-sha256 … --request … [--execution-id …]`; fixture terminal evidence must match retained command identity, nonce/script and outcomes. Journal proves no repeated POST.
7. Produce both genuine rollback proofs with actual `bootstrap rollback-proof`, transfer both root-only files to each original node within their validity window, then run staged `bootstrap resume-source --incoming` on each original. Verify restoration of only original schedulers/helpers, unchanged CA/native identity/data, no reverse accounting copy and no green reactivation. Retain all command exit/status evidence, signed receipt hashes, boot/process/cgroup/mount audits, SQL reconciliation and bounded remote journals.

Every stage can fail independently. Runtime/infra fixes may change configuration and app bytes, so the current00528fe app is not designated the final acceptance artifact. No full application activation, source capture, native CA SDK proof, protected transfer, installed packet chain or reverse handoff is claimed by this design.
